# S4 提案后验

> ## ⚠️ 复审揪出的 1 个 blocker + 6 个 major（都已修，写在这防重犯）
>
> ### 🔴 blocker：「刚批准还没跑起来」被**永久**写死成 `never_armed`
> `apply_strategy_proposal` 生成的是**草稿、不启用**，run 行只由引擎 tick 写
> （默认 30 分钟一次）。所以「applied 但一条 run 都没有」是**每一份提案的必经常态**。
> 而 `never_armed` 在 `_TERMINAL_UNABLE` 里、回填永不重扫 —— Jason 或 AI 在这个空档里
> 问一句「你提的建议准不准」（`refresh=True` 是默认值），这份提案就被永久销号，
> 之后跑满 30 天赚了钱也再不会被重评。
> **最新的提案反而是最容易被误销号的那一份**，正好把「拿账户余额给 AI 打分」打成反面。
> → 判定挪到窗口判定**之后**：窗口没满 + 没 run → `pending`（可重试）；
> 窗口走完还没 run 才是终态 `never_armed`。
>
> ### 🟠 major
> 1. **paper 的 hit 和真钱的 hit 长得一模一样** —— `_actuals` 算出了 `basis` 却没落库，
>    库里 / `list_strategy_proposals` / scorecard 分桶里**都看不出这是模拟盘**，
>    违反项目自己的铁律「`basis` 一定要跟着数字一起读」。
>    → 加 `outcome_basis` 列 + scorecard 按 `outcome:basis` 再分一层 +
>    `decided_with_real_money`。⛔ 不采用「paper 一律判 unable」：竞技场里新版本的正常
>    去处就是先进 paper 池，那样等于永远评不出东西；**分桶比丢弃诚实**。
> 2. **paper 走历史窗口会静默低估收益** —— `_paper_legs(_runs(sid, since, until))` 把
>    窗口外的买入腿切掉 → `costed = min(sold, 0) = 0` → 那笔平仓不记。
>    实测「窗口外买 1@100 + 窗口内买 1@100 + 窗口内卖 2@200」：真实 +199.4，算出 +99.7。
>    偏差方向**恒为低估** → 系统性地把 hit 判成 miss。这正是 live 侧特意防住的坑，
>    paper 侧没有对应保护，而 S4 是第一个传历史窗口的调用方。
> 3. **收口带来的读路径回归**：`source="crypto"` 收窄成「只剩自动策略引擎的单」，
>    对话下的 crypto 单进了 `moneybill`。真源表的 label 没跟上 →
>    `get_decision_history(source="crypto")` 会**静默少报**。
> 4. **本卡最核心的 since/until 管线，测试覆盖为零** —— 变异测试里
>    「去掉 since/until」「窗口末端贴到现在」全部存活。原用例只断言了
>    `evaluate_proposal` 自己拼的 `window` 字典，**从没碰过取数路径**。
>    → 重写成真闸门（窗口内赚 100、窗口外赚 9999，切错就拿到 9999），已验证会红。
> 5. **「不报百分比」只测了不会泄漏的那条分支** —— 把 `hit+miss>0` 分支换成
>    `f"兑现率 {hit/(hit+miss):.0%}"`，全套照过。→ 补覆盖，已验证会红。
> 6. 负预期时容差符号反了（预期 −2% → 门槛 −1.6%，实际 −1.8%**比承诺好**反被判 miss）。
>
> ### 另修（minor）
> `window` 用 `utc_iso` 而非裸 `isoformat`；`decision_tools` 里「同一张单有两条留痕」
> 那句**收口后已失真**且会随 `exec_overview` 进 LLM 上下文；重复索引
> （`ix_crypto_proposal_outcome` 与模型自动生成的重名不同名）；窗口未满时标 `partial`；
> scorecard 的分项加不回总数（漏了 `unevaluated` 桶）；tool_groups 描述。
>
> ### 🐌 顺带查清一件事
> 那次「测试跑了 16 分钟」不是代码慢 —— 是**失败断言让 pytest 对着 30KB 的模块源码
> 做反省**。断言改成 AST 计数后 0.7 秒。⚠️ 别在 assert 表达式里放大字符串。

> **一句话**：S2 让每份提案带上了「预期收益 / 预期胜率 / 多少天内兑现」——
> 这三个数让提案成为**可证伪断言**。这张卡把断言真的拿去证伪。
>
> ⭐ `00-PLAN §3` 裁决 13：**这是直接拿账户余额给 AI 打分**，
> 比「cockpit 说 BUY 后来涨没涨」跟钱的关系近得多。

## 1. 为什么不能塞进 `common/outcome_eval.py`

裁决 14 写得很清楚，这里补上具体原因：

| | `outcome_eval` 评的东西 | 策略提案 |
|---|---|---|
| 对象 | 一条建议：symbol + entry_price + 方向 | 一次**参数变更** |
| 窗口 | 5/20 个**交易日** | 提案自己声明的 `horizon_days`（自然日） |
| 判定 | 未来价 vs 入场价，含止损/止盈先触发 | 实际收益/胜率 vs **预期**收益/胜率 |
| 数据源 | 日线 bar | 该策略的**日收益率序列**（S3 建的） |

**没有 symbol、没有 entry_price、没有 bar。** 硬塞进去只会把那个已经被 P0-4 焊过两遍的
内核再撬开一次。→ 新建 `crypto_strategy/proposal_outcome.py`，独立 `ENGINE_VERSION`。

## 2. 判定口径

```
窗口 = decided_at .. decided_at + horizon_days（自然日，crypto 7×24）
实际收益 = 新版本在窗口内的日收益率之和
实际胜率 = 窗口内盈利平仓腿 / 总平仓腿
```

四态（对齐 `outcome_eval` 的形制，但值域独立）：

| outcome | 什么时候 |
|---|---|
| `hit` | 实际收益 ≥ 预期 × 容差 **且** 实际胜率 ≥ 预期 × 容差 |
| `miss` | 窗口满了，但没达到 |
| `pending` | 窗口还没满 |
| `unable` | 窗口满了却算不出来（没成交 / 明细没同步 / 新版本从没被 arm） |

### 2.1 三个必须防的自欺

1. 🔴 **「没上线」不是「没达到」**。提案被批准 ≠ 新版本被 arm（S2 刻意把这两件事分开）。
   一份从没上线的提案**没有可证伪的对象** → `unable`，⛔ 不许算成 `miss`。
   不这么分的话，AI 的提案胜率会被一堆「Jason 压根没让它跑」拉低，那不是 AI 的错。
2. 🔴 **容差不能设成 1.0**。「预期 +8%，实际 +7.99%」判 miss 是在惩罚精确度而不是判断力。
   默认 0.8（拿到预期的八成算兑现），可配。
3. 🔴 **样本永远不够，别在 UI 上摆一个假装有统计意义的胜率**（`00-PLAN §4` 问题 2：
   一年 12-24 条提案，而 P0-3 的门槛是 ≥30 样本）。
   → 明确定位成**定性参考**：报 `hit/miss` 的**计数**，不报「AI 提案胜率 62%」。

## 3. 双重留痕收口（P0-4 批次3 的写入侧）

现状（P0-4 迁出时实测）：同一张单会留**两条** DecisionLog ——
`crypto_intel_engine/execution.py` 一条（人话在 `output_text`），
`agents/confirm_gate.py` 再一条（结构化在 `output_summary`）。
S0 已经靠 `distinct_orders` 让计数不撒谎，但根子还在。

⛔ **不能靠「删 crypto 侧」解决**：`record_crypto_trade/resting` 有**两个调用方**——
`crypto_tools.place_crypto_order`（走 confirm_gate → 双重）与
`crypto_strategy/pending.py`（**不走 confirm_gate** → 只有这一条）。
删了 crypto 侧，半自动策略引擎的下单留痕直接断线。

→ **内层加 `log_decision` 开关**：`crypto_tools` 传 `False`（confirm_gate 那条信息更全 ——
带 session_id / turn_start_idx / model_id / data_quality / 完整 input_snapshot），
`pending.py` 保持 `True`。

⚠️ 代价：crypto 行那句人话（「币安限价单挂出（未成交，盘口等待撮合）」）会丢 ——
→ 让 `place_crypto_order` 的返回 `data` 带一个 `exec_note`，confirm_gate 记
`output_summary` 时自然带走。**不补这一步就是拿可读性换整洁，不划算。**
