> ### 2. 顺手修掉两处「文档与代码不一致」
> - `api/routes/data.py` 的设置项说明写着「1.0 all-in」——改完之后 1.0 只等于

>
> ### 3. §2.6 有一处说法要更正
> 卡里写 `get_decision_history` 裁掉了 `reasons` —— **没有，`reasons` 一直在返回里**。
> 真正永久看不见的是 `input_snapshot` / `output_summary` / `output_text` 三项。
>
> ### 4. `exec_state` 落成**四值**不是三值，并额外派生了 `order_id`
> 「币安市价单零成交」既没成交也没挂住，硬塞进三分类里就是说瞎话 → 加 `unknown`。
> 另外双重留痕（S4 才收口）会让「5 张单」被数成「10 条 resting」，所以顺手派生
> `order_id` 并在 `exec_overview` 里给 `distinct_orders`：**在收口之前，至少别让计数撒谎**。
> 生产库实测：16 条回执 = **6 blocked + 10 resting 留痕，真单 5 张**。
>
> ### 5. 🔴 代码审查揪出的三个 major（都已修，写在这防重犯）
> 1. **`exec_overview` 第一版建在被 `limit` 截断的样本上** → `distinct_orders`
>    随 limit 变（实测 5→2 / 10→4 / 50→5，真相 5），旁边还摆着全量的 `total`。
>    这正是 `get_decision_stats` docstring 明令禁止的那种数字。改成**独立的全量查询**，
>    并在返回里标 `scope: "all_matching"`。
> 2. **`state_unknown` 被判成 `blocked`** —— `place_crypto_order` 在「请求发出但超时
>    回查未果」时返 `{state_unknown, reason}`，它自己的文案写着「**这笔单可能已经成交**」。
>    按 `reason` 判成 blocked 等于告诉 LLM「钱没动」，而这是**唯一一个钱可能真动了**的状态。
>    判定顺序改成 `state_unknown` 压过 `reason`。
> 3. **AST 门禁被 `from decision_log import record_decision as rd` 绕过** ——
>    实测这么写一个脏 source 的写入点，门禁十条全绿。已改成先收集 `asname` 再匹配调用名，
>    且前缀过滤不带 `(`（import 那行没有括号，带括号会在读 AST 前就跳过整个文件）。

> `filled`）；`init_db` 那条 entry_kind 归类 SQL 是**第四张手写清单**（`ELSE 'advice'`
> 兜底 → 新的 execution 类 source 会被兜进胜率分母），已上门禁；指路文案里的 Python
> list repr、`verbose` 静默失效、未登记 source 被凭空说成「只有既成事实」也一并修掉。
>
> ### 6. 一处更正：crypto 的置信度**校准从来没坏过**

### 1.3 🔴 **本卡必须动一处代码**：现有实现做不到「单笔无上限 + 留 20% 现金」

写卡时核实发现的**真陷阱**——`trading_engine/risk/adapter.py:54-63`：

```python
def get_effective_risk_config():
    """单股上限设大时，总仓位上限同步抬到 ≥ 单股上限（避免 all-in 100% 误报）。"""
    pct = get_max_position_pct()                                    # 从 UserSettings 读
    cfg["max_position_pct"] = pct
    cfg["max_total_position_pct"] = max(cfg.get("max_total_position_pct", 0.8), pct)
    #                                    ↑ 单股上限会把总仓位上限**顶上去**
```

**后果**：Jason 按新规则去设置页把 `max_position_pct` 调到 `1.0`（取消单笔上限）
→ `max_total_position_pct` 自动变成 `1.0` → **20% 现金保护被静默撤销**。

**这正好是 Jason 特意叮嘱「别记错」的那个组合，而现有代码恰恰做不到它。**

→ **处置**：解耦这两个值。总仓位上限（0.8）是**独立的硬底线**，不该被单股上限抬高。
方向应该反过来——单股上限受总仓位上限约束（`min`），而不是去抬高它。

⚠️ 顺带记录一处**文档与代码长期不一致**：`CLAUDE.md` 写单股 ≤ 20%、
`trading_engine/config.py:9` 默认也是 `0.20`，但 `UserSettings` 里 Jason 实际设的是 **50%**
（实测风控日志：`持仓比例 2413.82% 将超过限制 50.00%`）。改完文档后这条不一致仍在，
但因为单股上限本身要取消，它会自然消失。

## 2. 查询侧可见性（P0-4 批次3 迁入，**写入侧留给 S4**）

> **划分口径**：本卡只动 `get_decision_history` 这一个工具（读）。
> 「双重留痕收口」「归因维度」要动写入点和数据模型 → **S4**。

### 2.1 🔴 问题 1：`_SOURCES` 手写枚举漏了 crypto——且这是同款成因

`agents/tools/decision_tools.py:16`：

```python
_SOURCES = Literal["advisor", "cockpit", "moneybill", "moneybill_recommend", "report_picks"]
```

**漏了 4 个**（不是 3 个）：`crypto`、`crypto_cockpit`、`crypto_earn`，
以及实际存在但从没列进去的组合。全集实测 8 个：

```
advisor / cockpit / crypto_cockpit / moneybill_recommend / report_picks   ← advice 类
moneybill / crypto                                                        ← execution 类
crypto_earn                                                               ← ops 类
```

**后果**：MoneyBill **根本没法按 crypto 查胜率**。注意不是完全看不到——不传 source 时
`by_source` 里其实有 `crypto_cockpit` 的数字；真正丢的是**过滤能力**和 **per-source 的
calibration**（`compute_calibration(source=...)` 传不进去 → 永远只看 cockpit）。

⭐ **但更要命的是它是手写枚举、靠人记得同步——跟 `entry_kind` 那颗炸弹同款成因。**
补完这次，下一个新 source 照样会漏。所以：

### 2.2 做法：建 source 真源 + 两条门禁

| 类型 | 文件 | 做什么 |
|---|---|---|
| 新增 | `backend/common/decision_source.py` | `SOURCES: dict[str, dict]` —— source → `{label（中文说明）, kind（属于哪个 entry_kind）}`。对齐 `common/decision_kind.py` 的形制 |
| 修改 | `agents/tools/decision_tools.py` | `_SOURCES` Literal 仍手写（pydantic 要静态字面量），由门禁保证它 == 表的键集 |
| 新增 | `tests/test_decision_source_registry.py` | ① Literal ⇄ 表键集一致 ② **AST 扫全项目 `record_decision(` 的 `source=` 字面量必须都在表里** ③ 工具 description 里必须提到表中每个 source（防文案漂） |

门禁 ② 的范式**直接抄** `tests/test_decision_entry_kind.py::test_no_unclassified_record_decision_write_site`
（它已经在 AST 扫写入点了，顺手多取一个 `source=` 字面量即可）。

⚠️ 抄的时候连那条坑一起抄：**读源码 AST，不读运行期 `REGISTRY`**——别的测试会往全局
REGISTRY 塞假工具，读它会「单跑绿、全套红」。

### 2.3 🔴 问题 2：一个会静默返空的组合陷阱

`query_decisions` 默认 `entry_kind="advice"`。所以 LLM 传 `source="crypto"`
（想查 crypto 胜率）会拿到 **0 条 + 空 stats**，然后回答「没有 crypto 记录」——
而真正的 crypto 建议在 `crypto_cockpit`。

**静默的空结果比报错糟**（TurnMonitor 那条教训）。

→ **处置**：`SOURCES` 表里标了每个 source 的 kind。命中「这个 source 下只有回执/ops」时，
返 `business_result="negative"` 并**指路**：「crypto 的订单回执在 `crypto`，
AI 建议在 `crypto_cockpit`，你要问的胜率应该查后者」。

### 2.4 开 `entry_kind` 入参

```python
entry_kind: Literal["advice", "execution", "ops", "all"] = "advice"   # "all" → 传 None
```

⭐ **裁决：它只作用于样本列表；`stats` 与 `calibration` 恒定只算 advice**，
返回里显式标 `stats_scope: "advice"`。

理由：胜率的定义就是「AI 建议准不准」。让 LLM 能算出「订单回执的胜率」，
等于把 P0-4 批次1 刚焊死的口径又开一条缝。

### 2.5 加 `exec_state` 派生字段（**纯读侧，不加列、不迁移、不改写入点**）

**为什么要有**：开了 `entry_kind="execution"` 之后，Jason 问「我下过哪些单」会拿到
16 条**长得一模一样的 `executed=false`**。但实测真相是三种完全不同的事：

| 派生值 | 实测条数 | 判定 | 意味着什么 |
|---|---|---|---|
| `blocked` | **6** | `output_summary.reason` 有值 | **根本没到交易所**（风控拦下 / `金额 4.97 低于最小名义额 5.0`）。钱没动 |
| `resting` | **5** | `output_summary.resting` 为真 | 真挂在币安盘口等撮合 —— **可能现在还挂着** |
| `filled` | **0** | `executed=1` | 成交 |

不做这个，「可见性」名不副实：**LLM 只会说「你有 16 笔未成交订单」，而真相是只有 5 张单。**

信息全在 `output_summary` 里躺着，只是没结构化。

### 2.6 加 `verbose` 入参

**为什么要有**：`get_decision_history` 刻意裁掉了 `input_snapshot` / `output_summary` /
`output_text` / `reasons` 全文，注释写的理由是：

```python
# 精简回灌 LLM：去掉大字段（完整快照留在 /decisions 页面看）
```

**实测：`api/routes/` 里没有任何 route 暴露 DecisionLog，`frontend/src/pages/` 里没有
`/decisions` 页面。** 那个理由的前提不存在 → **完整快照现在永久看不见**。

→ `verbose: bool = False`，**仅当 `limit <= 3` 时生效**（限死条数，否则 token 会炸），
返回完整快照。同时把那句过期注释改成实话。

⭐ 这样补缺口**不用开新页面/route**，符合 `00-PLAN §2` 铁律第 1 条。
