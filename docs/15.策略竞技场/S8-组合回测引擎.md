# S8 组合回测引擎

> **一句话**：现在的「多标的回测」是**逐币各发一份完整本金独立跑，再把收益率平均**。
> 没有资金竞争、没有「A 占了钱 B 就买不了」——所以任何带权重的组合策略，
> 回测出来的数字**跟权重毫无关系**。

---

### 0.4 🔴 `per_symbol_exposure_cap_pct` 从来没被回测验证过

```python

```

DSL 里声明了单币敞口上限 15%，但**逐票独立回测时每个币都有完整一份本金**，
所以这条约束在回测里等于不存在。组合回测跑起来之后它才第一次真正生效

### 0.5 ⚠️ 「整数股 + 100 股一手」这条 A 股假设，被抄了 8 份

```cpp

```

`ma_cross` / `macd` / `rsi`(在 server 里) / `kdj` / `bollinger` / `momentum` /
`combo` / `pairs` / `external_signal`。crypto 现在靠 `crypto_intel_engine/backtest.py`
的**价格缩放**绕过（把 bar 价格 × k 缩到 $10 量级）。

🔴 **共享资金池会把这个近似的误差放大**：

| 本金 | 币数 | 每个币名义额 | 缩放后单价 | 手数 | 取整误差上界 |
|---|---|---|---|---|---|
| $10 万 | 1（现状） | $10 万 | $10 | 1000 手 | 0.1% |
| $10 万 | 5 | $2 万 | $10 | 20 手 | **5%** |
| $10 万 | 10 | $1 万 | $10 | 10 手 | **10%** |

→ **Jason 2026-07-31 拍板：每手股数按市场配**（crypto → 1 股一手，A 股保持 100）。
改动小，取整误差降到 0.01% 级。⛔ 不上浮点数量（那要动 portfolio/engine/metrics/
全部策略/全部测试，是另一张卡的体量）。

### 0.6 🔒 C++ 的 `RiskConfig` 没有「总仓位」概念

```cpp
// types.h:313-319
struct RiskConfig {
    bool   enabled = false;
    double stop_loss_pct = 0.05;
    bool   trailing_stop = false;
    double trailing_stop_pct = 0.08;
    double max_position_pct = 1.0;      // ← 只有单股上限
};
```

→ **Jason 2026-07-31 拍板：加 `max_total_position_pct`，回测口径必须跟实盘一致。**
⚠️ 代价说清楚：现有策略的回测收益会**系统性下降**（以前能满仓）。
但反过来说，现在的回测数字本来就是实盘做不到的 —— **高估在先**。

🔴 **动这里必须先读 `risk-total-position-floor` 那条记忆**：
`max(总仓位上限, 单股上限)` 会**静默撤销现金保护**，这个 bug 在 Python 侧被复制过三份。
C++ 这份**必须写成「两条独立约束，取更严的那个」**，⛔ 绝不能是 max。

### 0.7 组合策略 DSL 不存在

`CryptoStrategySpec` 只有 `universe.symbols`（一个白名单），**没有子策略、没有权重**。
裁决 6 说的「60% 趋势 + 40% 均值回归」在 DSL 里**表达不出来**。

## 2. 设计

### 2.1 核心语义：同一天多个买单抢同一份现金

这是整张卡的灵魂。逐票独立回测里不存在这个问题，组合回测里**每天都要面对**。

```
第 T 天：BTC 说「买 95% 现金」、ETH 说「买 95% 现金」、SOL 说「买 95% 现金」
         → 请求合计 285%，而现金只有 100%
```

**处置：先卖后买 + 买单按请求名义额等比缩减。**

- **先卖后买**：卖出释放的现金，同一天可以被买单用上（真实世界 T+0 现金可用；
  A 股的 T+1 限制的是**股票**不是现金，`settle_t1` 已经在管股票那一侧）
- **等比缩减**：不用「先到先得」——那样**按 symbol 字母序**决定谁买得到，
  BTC 永远排在 SOL 前面，是个隐形的系统性偏袒
- ⛔ **不静默**：缩减了多少天、削掉多少名义额，记进结果的 `cash_contention`

### 2.2 联合交易日历：缺 bar ≠ 数据是 0

不同标的的 bar 日期不一定齐（crypto 7×24 vs 股票；新币上市晚；停牌）。

- 逐**日期**推进，不逐 index
- 某标的当天没有 bar → **跳过它当天的决策**，但持仓市值**沿用最后一次成交价**
- ⛔ 绝不能把缺失当 0 —— 那会让净值曲线在缺 bar 那天凭空塌陷
- 结果里带 `bar_coverage`：每个标的实际有多少天有 bar

### 2.3 策略接口：不动 `IStrategy`

**每个标的每天各调一次 `on_bar(ctx)`**，`ctx.cash` 反映的是**共享现金的当前余额**。
资金竞争因此天然发生，而 8 个现有策略**一行都不用改**。

⭐ 这是刻意选的最小侵入路径。代价是策略看不到「别的标的怎么样」——
真正需要跨标的视野的策略（配对、组合权重）走 §2.5 的子策略机制。

### 2.4 每手股数：收成一处

`StrategyContext` 加 `lot_size`（由 market 决定），8 处 `/100)*100` 全部改成
`ctx.lot_floor(...)`。加门禁抓「又有人手写 100」。

### 2.5 组合策略 DSL

```python
class SubStrategy(BaseModel):
    name: str
    weight: float            # 0~1，同一 spec 内合计 = 1.0
    universe: Universe | None = None   # 不填则继承顶层
    entry_rules: EntryRules
    exit_rules: ExitRules

class CryptoStrategySpec(BaseModel):
    ...
    sub_strategies: list[SubStrategy] | None = None
```

- 有 `sub_strategies` 时，顶层 `entry_rules`/`exit_rules` 必须缺席（互斥，validator 强制）
- 每条子策略拿到 `weight × 初始本金`作为**自己的预算上限**
- ⚠️ 子策略之间**共享同一个 Portfolio**（一份现金、一份持仓表），
  预算只是**软上限**（限制它能请求多少），不是各自独立的钱包 ——
  否则又退回「每人一份本金」的老问题

## 3b. 批次 1 实施记录（2026-07-31，审查发现逐条已修）

### 🔴 两个 blocker：20% 现金底线曾经是**纸面上的**

第一版把「总仓位上限」写进了闸门，但有两条路绕过去：

1. **同一天多个买单**：闸门是无状态的，不会替调用方扣额度。第一版在开盘时算
   一次总仓位快照，然后每个买单都拿这份快照去过闸门 → N 个买单**各自**都在
   80% 以内、**合计**顶到 100%。实测三个标的同日各请求 35%，现金被打到 **0.1 块**。
   ⭐ 而且资金竞争的等比缩减 `scale = cash/need` 的目标就是**花光现金**，
   所以「缩减只会变小所以安全」这个假设是**错的** —— 它跟 80% 上限正交。
   修法：闸门循环里**逐单累加已放行名义额**。

2. **隔夜跳空时价基混用**：闸门用今日开盘价核验，但「当前总仓位」取自
   `portfolio.get_market_value()`，那时还是**昨收**标记的（今天的 `update_price`
   在下一步才跑）。实测持仓隔夜从 10 跳到 40，账面已经 92%，闸门按昨收算
   还觉得有三万块空间，照放。修法：按今日开盘价重新标一遍再判。

⚠️ 第一版的测试之所以全绿，是因为它把两个买单排在**不同的两天** ——
恰好是这个 bug 唯一不咬人的排法。

### 🟠 `enabled` 曾经能把现金保护整条关掉

`filter_buy_quantity` 第一行是 `if (!config_.enabled) return requested_qty;`，
而 `enabled` 的**服务端默认值是 false**。于是 `max_total_position_pct=0.8`
配了等于没配，且看不出来。

→ 口径改成：**`enabled` 只管止损那套，仓位上限是账户结构约束，哪条配成 <1.0
哪条就生效**。两条都是默认 1.0 时行为与从前一致。

### 🟠 四个 helper 抽出来了，主端点却没用上

`/api/backtest/run`（`walk_forward` / `backtest_cpp_client` / `api/routes/backtest_cpp`
全走它）保留着自己那份 inline 的风控解析 → **读不到 `max_total_position_pct`、
也拿不到 `MarketRules`**（market=crypto 时一手仍是 100 股）。已改成三个端点共用同一套。

### ⚠️ 批次 1 就已经改变了 crypto 回测的数字

`/run_signals` 现在给 crypto 传 lot=1，而价格缩放那层还在 → 最小成交额从
~$1000 掉到 ~$10。**S3 竞技场的四道门槛读的就是这个 gate 的数字**，
从这次改动起跟历史不可比。

→ 处置：结果 JSON 里带 `engine_version: "cpp-backtest-v2-portfolio"`，
别让两代数字混着看。（口径变更的完整说明仍在批次 2。）

## 3c. 批次 2 实施记录（2026-07-31，审查发现逐条已修）

### 🔴 blocker：谁拿到钱由**字母序**决定，而且能把 `passed` 翻号

批次 1 把总仓位额度写成了「逐单先到先得」（每放行一单就累加 `total_pos_now`），
而 `buys` 的顺序来自 `std::map` = **字母序**。§2.1 承诺的等比缩减只在
`need > cash` 时才跑 —— **额度卡住时账上现金还剩着，那条路根本不触发**。

实测 8 个币同日各请求 95%（15% 单币 / 80% 总仓）：
前五个各拿 15%、第六个拿 5%、**最后两个一单都没买到**，而
`cash_contention = {days: 0}` —— 全程静默。

**翻号反例**：6 个慢跌的币 + 1 个大赢家 ZZZ

| 口径 | net_return | passed |
|---|---|---|
| 旧（各币独立收益平均） | +3.03% | ✅ |
| 新（共享资金池） | **−2.71%** | ❌ |
| 新，只把赢家改名叫 `AAA_WIN` | **+3.88%** | ✅ |

真实 universe 里 `BTCUSDT.BN < ETHUSDT.BN < SOLUSDT.BN` —— **BTC 永远赢**。
而 `passed` 正是 S3 竞技场门槛③ 读的那个布尔。

→ 已修：拆出 `filter_symbol_quantity`（单标的上限逐单独立判，顺序无关），
总仓位额度**按请求名义额等比分配**；新增 `cap_contention` 单独计数
（⚠️ 与 `cash_contention` 是两件事，混在一起就是上面那个静默）。

### 🟠 口径标记曾是装饰品

`basis` / `engine_version` **零消费方** —— 落库那层（`_apply_backtest` 与
`run_and_store_backtest`，两处各抄一份）只写 `metrics/degraded/caveats/per_symbol`，
标记全被丢掉。于是库里 S8 前后的行**结构上无法区分**：同一列、同一个 JSON、含义已换。

→ 已修：抽出 `backtest_metrics_json()` 一处序列化（两处从前各抄一份，
加字段极易只改一边），`basis`/`engine_version`/两个 contention 全部落库。

⚠️ 顺带更正一处我写错的注释：「S3 竞技场读的就是它」是**错的** ——
arena 只读 `backtest_passed` 这个布尔，一个数值字段都不读。

### 🟠 「缩放不变」的说法本身是错的

我原本的 docstring 写「现金/总资产/净值/收益率/夏普/回撤**全部**与 k 无关」。
审查直接打端点证伪：同一条走势，价位从 100 抬到 1e4 → `total_return`
从 0.0984 掉到 0.0745（**相对偏差 24%**）；同一次组合里混两个差 100 倍的 k →
0.1968 vs 0.1729。根因是整数股取整，不变性只成立到 **O(close·k / 本金)** 的粒度。

→ 正确的说法是：**保证正确性的不是「不变性成立」，而是 `_pick_scale` 逐币把价格
归一到同一量级，账本因此永远见不到混合量纲**。docstring 已改写，测试也重写成
测这条真性质（价位换成 64000/0.0015 收益不变 + 各腿缩放后量级对齐）。

### 🟠 一根脏的首 bar 能让整个币静默消失

`_pick_scale` 按**首根 close** 定 k：`close=1e-8` 打头 → k=1e9 → 后续价格全变 6e13
→ 算出 0 股 → **一单不下、零异常、零日志**。在 10 个币的组合里它只表现为
「收益率略低」。→ 改成按**中位数**取；并新增 caveat 点名「整个回测期一单没下」的币。

### 🔴 顺手挖出：本机服务调用全部走了 Clash

`.env` 有 `HTTP_PROXY=127.0.0.1:7897` 且**没有 `NO_PROXY`**，而
`load_dotenv(override=True)` 全项目六七处 —— 于是 `requests`/`httpx`
（`trust_env` 默认 True）把 **localhost:8002（C++ 回测）** 和
**localhost:8001（订单簿撮合）** 也塞进代理。Clash 没开时链路直接断，
报 `ProxyError`，看上去完全不像那个服务的问题。三处全修 + 门禁。

⚠️ 修的时候又踩一个：`requests` 会对传进去的 proxies dict 做**原地 setdefault**，
共用一个模块级常量会被环境里其它 scheme 的代理污染（实测跑完整套测试后
多出一个 `knowledge_overseas` 键）。改成每次返回新 dict。

## 3d. 批次 3 实施记录（组合策略 DSL）

### 🔴 v1 硬限制：子策略的 universe **不许重叠**

裁决 6 举的例子是「60% 趋势 + 40% 均值回归」，而经典写法是**同一批币、两套规则**。
**v1 表达不了这个**，只能表达「这几个币走趋势、那几个币走均值回归」。

原因：交易所侧**一个币只有一个仓位**。同一个币被两条子策略各管一半时，
同一根 bar 上 A 说买、B 说卖**无法净额处理** ——「A 持 0.5 BTC、B 持 −0.3 BTC」
在现货上根本不存在（引擎不支持做空）。要支持重叠得先有一层「仓位归属」账本。

⛔ 别为了绕过这条限制去掉校验：去掉之后回测数字会变成一个说不清含义的东西。
重叠时编译期直接报错并说明理由。

### ⭐ `rule_sets()`：单策略与组合策略在下游长成同一个形状

单策略 → 一条 `weight=1.0` 的 `RuleSet`；组合策略 → N 条。于是回测闸 / 逐日回放 /
实盘引擎 / agent 工具都只写一套「遍历 rule_sets」的逻辑，不用到处
`if spec.sub_strategies:` 分叉 —— **那种分叉迟早漏一处**（实施时就漏了
`_non_replayable_fields`，被测试当场抓出来）。

### 权重怎么真的起作用

- **回测**：`_stamp_weight` 把子策略权重盖到买入信号的 `weight` 字段上，
  于是 60/40 直接体现在请求名义额上。⛔ 别改成「按权重把本金切成 N 份各自独立跑」——
  那就退回 S8 要解决的老问题了。
- **实盘**：`_decide_symbol` 用 `owner_of(symbol)` 找到归属规则集，
  仓位按 `weight × 总资金` 算。单策略 weight=1.0 → 行为与从前完全一致。
- ⚠️ 两处都是**软上限**（限制能请求多少），不是各自独立的钱包。

### 差点漏掉的两个

| 问题 | 后果 |
|---|---|
| `_spec_to_columns` 无条件 `.model_dump_json()` | 组合策略的 `entry_rules` 是 None → **落库当场 AttributeError** |
| `sub_strategies` 没有对应的列 | 权重**静默丢失**：存进去是组合策略，读回来是一条没有规则的空壳 |

已加列 + 自动迁移（存量行留 NULL = 单策略，`rule_sets()` 归一，无损）。

### 🔴 顺带补上：单币上限裁掉多少，此前**没有任何地方报出来**

用生产数据重跑时发现：`cap_contention` 是 0、`caveats` 是空，而单币 15% 上限
明明把请求削掉了约 85% —— 两个「没事」拼出一个假象。
根因是我那个字段只数「总额度不够时的等比分摊」，**不数「单币上限直接裁掉的部分」**。

已新增 `symbol_cap` 计数 + caveat，并特意写明：
**⚠️ 它会把收益和亏损一起按比例压向 0，别把跌幅收窄读成「策略变好了」。**
