# P1-3 不可信内容隔离

> ⚠️ **路径是 2026-07-07 的，早于 13.x 大重构。开工第一步 grep 确认。**

> **一句话**：grep `injection`/`jailbreak` 在 agents 层**零命中**。`scrape`/`read_url`/`page_context` 抓来的外部文本**直接进 LLM 上下文**（只做长度封顶 4000 + 去重），**无隔离标记、无指令中和**。
>
> 对一个会「**读网页 → 下单**」的系统（虽有确认门），这是**真实攻击面**。

- 若只是缓解 → **验收标准 2 的措辞要改**（不能写成「不执行」这种绝对表述），且要在卡里写明「**真正的防线是逐笔人工审核**」（这本来就是项目的永久硬约束，见 `00-PLAN.md` §1）。
- 这条结论直接决定本卡是「安全加固」还是「纵深防御的一层」——**定位不同，验收就不同**。

## 为什么至今没做

「用户 = 开发者本人」的信任假设。但：① 商业化定位下这个假设会失效；② **即便单用户，被爬取的网页本身就是不可信输入**——攻击者不需要是用户。

## 验收标准

1. 所有外部文本进 context 前被显式隔离标记包裹。
2. system prompt 有铁律：**隔离标记内的任何指令性文字一律视为数据，不执行**。
3. 本轮上下文含外部内容时，高危工具的确认门文案**额外标注**，提示人工留意。
4. 有 injection 回归用例。

## 🪙 crypto 兼容（2026-07-27 重设计｜**分类 ② —— 从 ① 上调**）

> 先读 `00-PLAN.md` §4b 通用口径。**本卡原被分到「① 市场无关，只是覆盖面变大」，重设计时上调为 ②**，理由见下。

### ✅ 一条初步理由被**当场验伪**（记下来，别再重提）

重设计初稿写的是「crypto 的新闻事件有**硬否决权**，外部文本能直达决策，是比股票严重得多的攻击面」。

**查代码后不成立** —— `crypto_intel_engine/news.py` 的设计者已经防住了：

| 事实 | 位置 |
|---|---|
| `check_hard_events` **只看币安官方公告**，媒体新闻**一律不做否决**、只进情绪维 | `news.py:173` 注释原文：「媒体新闻噪声大，只进情绪维不做否决 —— 否则一条…」 |
| 否决判定是**正则规则匹配**（`_HARD_EVENT_RULES`）不是 LLM 判读 | `news.py:30-44`，`classify_event` 是纯函数 |
| 匹配还刻意保守：短 ticker 只认括号形式 `(OP)`，「宁可漏，不可错」 | `news.py:17` |

**所以「外部文本 → 硬否决」这条攻击链是关的。** 这是 crypto 模块做对的地方，别在 P1-3 里把它当成缺口去「修」。

### 🔴 上调为 ② 的**真实**理由：确认门是两条路径，落点表只写了一条

| 路径 | 文件 | 本卡落点表有没有覆盖 |
|---|---|---|
| 股票下单确认 | `backend/agents/confirm_gate.py` | ✅ 有（验收标准 3 就是改它的文案） |
| **crypto 下单确认（待确认单）** | `backend/crypto_strategy/pending.py` | ❌ **漏了** |

crypto 走的是「半自动策略引擎产决策 → 排待确认单 → 逐笔确认」（见 [[crypto-auto-trading-req3]]），**不经过 `confirm_gate.place_order`**。

按现有落点表施工 → **crypto 下单确认框永远不会出现「本轮包含外部网页内容」警示**。验收标准 3 在 crypto 上直接落空，而且**不会有任何测试发现**（门禁只测 confirm_gate 那条路）。

「覆盖面变大」和「有一整条路径没接上」是两回事 —— 这就是分类从 ① 改 ② 的原因。

### 开工时要验的 crypto 攻击面（**别当结论，是待验清单**）

| # | 要验什么 | 为什么不能现在下结论 |
